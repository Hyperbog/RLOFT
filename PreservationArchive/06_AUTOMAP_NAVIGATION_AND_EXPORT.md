## 2. Automap state exists in three layers

The automap is not one array.

The original engine has at least three conceptually distinct layers:

```text
1. authoritative world/discovery state
       16-bit cell words at 0x198E0

2. generated map-class cache
       uint8 cache at 0x1760

3. presentation/export resolution
       connected-wall/door/inset classes
       on-screen rendering
       CP437 text glyphs
       object overlays
       annotation overlays
```

The standalone level writer serializes the cell words, later calls classifier `01558`, and then writes the generated byte cache. This proves the cache is derived state rather than independent topology. [CELL_WORD.md](https://github.com/Hyperbog/RLOFT/blob/373c7f10e6fc0f29c1e805125ef048150fcc7ba7/DatFiles/LEVELS.DAT/CELL_WORD.md) [Automap reconstruction](https://github.com/Hyperbog/RLOFT/blob/dedebcbbe43b435e989e05c0a8b1ff9b8a611245/DatFiles/LEVELS.DAT/AUTOMAP.md)

A faithful implementation should preserve all three layers instead of treating a saved cache byte as the permanent semantic identity of a map cell.

## 3. Current visibility and persistent exploration are separate cell bits

The 16-bit cell word contains:

```text
0x0040  current first-person visibility/raycast mark
0x0400  persistent automap explored/revealed mark
```

First-person traversal sets both bits on reached cells:

```text
cell |= 0x0440
```

Later renderer reset clears `0x0040` map-wide while retaining `0x0400`. [CELL_WORD.md](https://github.com/Hyperbog/RLOFT/blob/373c7f10e6fc0f29c1e805125ef048150fcc7ba7/DatFiles/LEVELS.DAT/CELL_WORD.md)

The exact conceptual distinction is therefore:

```text
0x0040
    currently reached/visible during the active first-person traversal

0x0400
    persistently discovered for automap purposes
```

The supplied `LEV022.DAT` independently demonstrates persistence: 313 saved cells carry the exploration/current-visibility delta `0x0440` relative to the compact archive baseline. [LEV022 mutable delta](https://github.com/Hyperbog/RLOFT/blob/373c7f10e6fc0f29c1e805125ef048150fcc7ba7/DatFiles/LEV022.DAT/MUTABLE_DELTA.md)

## 4. Runtime automap data

The active automap path uses:

```text
0x198E0  uint16 cell_words[width*height]

0x1760   uint8 generated_map_cache[width*height]

0x12756  int16 automap_width
0x12754  int16 automap_height

0x25622  int16 primary_cell_resource_A[64]
0x25822  uint16 automap_style_control[64]

0xCB3C   first 10-byte cell-record group
0xCD3C   second/dynamic 10-byte cell-record group

0x5760   0x800-byte runtime annotation buffer

0x1274C  selected map/level ID in map browser
0x5FCB   selected-map-is-current flag
0x5FD9   annotation-text display toggle
```

[Automap reconstruction](https://github.com/Hyperbog/RLOFT/blob/dedebcbbe43b435e989e05c0a8b1ff9b8a611245/DatFiles/LEVELS.DAT/AUTOMAP.md)

The automap therefore depends on both persistent level serialization and current runtime globals.

## 5. Cache classifier `01558..01830`

The cache rebuild begins by copying live level dimensions into automap width/height and then iterates every cell.

For ordinary classification:

```text
index = row * width + column
word  = cell_words[index]
code  = word & 0x003F
default class = 0xFF
```

[Automap reconstruction](https://github.com/Hyperbog/RLOFT/blob/dedebcbbe43b435e989e05c0a8b1ff9b8a611245/DatFiles/LEVELS.DAT/AUTOMAP.md)

The classifier is not merely a direct table lookup. It incorporates:

- current party position;
- exploration state;
- raw six-bit cell code;
- primary cell resource lookup;
- secret/hidden topology;
- special dynamic-cell geometry;
- dynamic 10-byte record state;
- neighboring explored cells.

## 6. Party cell is explicitly detected

Direct CODE.2 instructions `015AA..015E3` first compare the iterated cell against the current player's live cell coordinates:

```text
row    == int16(DGROUP 0x255D6)
column == int16(DGROUP 0x255D2)
```

Only on that exact cell does the classifier use header/environment byte `0x258A8` to choose:

```text
if environment_profile_id_or_FF == 0xFF:
    class = 0x2F
else:
    class = 0x2E
```

[Automap reconstruction](https://github.com/Hyperbog/RLOFT/blob/dedebcbbe43b435e989e05c0a8b1ff9b8a611245/DatFiles/LEVELS.DAT/AUTOMAP.md) [Header tail](https://github.com/Hyperbog/RLOFT/blob/2cafc03090ffbf729ed61e17f53c247cef01d534/DatFiles/LEVELS.DAT/HEADER_TAIL.md)

Thus `0x2E/0x2F` are **party-cell classes whose variant depends on the level environment/render profile**.

The text exporter later maps both values to `0xFA`, so a saved textual automap deliberately loses the internal party-cell distinction and emits the ordinary floor glyph.

## 7. Explored-cell classification

For cells with persistent exploration bit `0x0400`, the classifier applies the following order:

```text
raw code == 0
    -> 0x2E / 0x2F

primary_cell_resource_A[code] == 0x0093
    -> 0x2E / 0x2F

cell has 0x0800 hidden/secret topology
    -> 0x05

cell does NOT have 0x0080 special geometry
    -> 0x01

cell has 0x0080 and no associated 10-byte record
    -> 0x03

cell has 0x0080 and dynamic query returns 0x8000
    -> 0x04

otherwise
    -> 0x02
```

[Automap reconstruction](https://github.com/Hyperbog/RLOFT/blob/dedebcbbe43b435e989e05c0a8b1ff9b8a611245/DatFiles/LEVELS.DAT/AUTOMAP.md)

These values are intermediate cache classes. They are not yet final on-screen or text-export glyphs.

## 8. Unexplored cells are usually `0xFF`

For an unexplored cell:

```text
raw code == 0
    -> remains 0xFF

primary_cell_resource_A[code] == 0x0093
    -> 0x2E / 0x2F in certified CODE.2

otherwise:
    inspect all eight neighboring cells

    if any neighbor:
        is explored (0x0400)
        AND has raw cell code 0

        -> boundary class 0x01

    else
        -> 0xFF
```

[Cache rebuild audit](https://github.com/Hyperbog/RLOFT/blob/373c7f10e6fc0f29c1e805125ef048150fcc7ba7/DatFiles/LEVELS.DAT/CACHE_REBUILD_AUDIT.md)

The neighbor test uses the **neighbor's raw six-bit code**, not the primary resource table. This matters for reproducing fog-of-war boundaries exactly.

## 9. `0x0093` is a classifier shortcut, not cell code

The value `0x0093` is tested in:

```text
primary_cell_resource_A[cell_code]
```

It is therefore a level-local resource-table value associated with a six-bit cell code, not itself the serialized cell code.

When encountered in the certified classifier, the cell takes the common `0x2E/0x2F` floor/party-class route even when the raw code is nonzero. [Cache rebuild audit](https://github.com/Hyperbog/RLOFT/blob/373c7f10e6fc0f29c1e805125ef048150fcc7ba7/DatFiles/LEVELS.DAT/CACHE_REBUILD_AUDIT.md)

This distinction is central to the known Level-22 cache discrepancy documented later.

## 10. Dynamic special-cell classification

For special cell bit `0x0080`, the automap and collision systems converge on the second 10-byte record group.

Dynamic query `1E930(cell_index)` returns:

```text
matching record:
    record[6] << 12

no matching record:
    0x8000
```

The dynamic record itself uses:

```text
record[6] == 0   open/passable endpoint
record[6] == 8   closed/blocking endpoint
record[6] 1..7   transitional, blocking in traced traversal
record[7]        signed animation delta
```

[Dynamic cell records](https://github.com/Hyperbog/RLOFT/blob/373c7f10e6fc0f29c1e805125ef048150fcc7ba7/DatFiles/LEVELS.DAT/DYNAMIC_CELL_RECORDS.md)

When a real group-2 record is present:

```text
record[6] == 8
    -> cache 0x04

record[6] != 8
    -> cache 0x02
```

but no matching dynamic record can also produce cache `0x04`. Therefore `0x04` is not universally synonymous with “closed door.”

## 11. Cache classes are resolved through connectivity

Before final presentation, classes below `0x20` enter resolver `009B0..00B6B`.

The resolver examines orthogonal neighbors and derives connectivity/floor-adjacency masks.

Certified class behavior:

```text
0x01
    generic connected wall/boundary
    -> table-driven resolved wall class

0x02
    aligned dynamic/special geometry
    -> 0x29 or 0x2B
    -> otherwise wall fallback

0x03
    inset-capable special geometry
    -> 0x20..0x23 based on floor-neighbor direction

0x04
    aligned dynamic/special geometry
    -> 0x28 or 0x2A
    -> otherwise wall fallback

0x05
    hidden/secret topology
    -> 0x33 when opposite-floor geometry qualifies
    -> otherwise wall fallback
```

[Automap reconstruction](https://github.com/Hyperbog/RLOFT/blob/dedebcbbe43b435e989e05c0a8b1ff9b8a611245/DatFiles/LEVELS.DAT/AUTOMAP.md)

This is why a single cache class can become different final glyph orientations depending on neighboring cells.

## 12. Hidden/secret passage path

Packed cell bit `0x0800` produces cache class `0x05` once explored.

Resolver class `0x05` can become resolved value `0x33` when the required opposite-floor topology is present. Otherwise it falls back to ordinary wall connectivity. [CELL_FLAG_LINKS.md](https://github.com/Hyperbog/RLOFT/blob/373c7f10e6fc0f29c1e805125ef048150fcc7ba7/DatFiles/LEVELS.DAT/CELL_FLAG_LINKS.md)

The text exporter maps resolved `0x33` to byte `0xB2`, independently identified in Ravenloft automap research as the IBM/DOS shaded-block glyph used for a secret door. The executable proves the value flow; community research supplies the human-readable historical map legend. [Automap reconstruction](https://github.com/Hyperbog/RLOFT/blob/dedebcbbe43b435e989e05c0a8b1ff9b8a611245/DatFiles/LEVELS.DAT/AUTOMAP.md)

Community source:  
<https://www.swordsandsoftware.com/ravenloft-automaps.php>

## 13. Inset and door resolution

Resolved values have direct export-byte mappings:

```text
0x20 -> 0xDF
0x21 -> 0xDC
0x22 -> 0xDD
0x23 -> 0xDE

0x28 -> 0xCD
0x29 -> 0xCD

0x2A -> 0xBA
0x2B -> 0xBA
```

The community automap study independently identifies:

```text
0xDC / 0xDD / 0xDE / 0xDF
    directional inset glyphs

0xCD
    horizontal door

0xBA
    vertical door
```

The orientation selection itself is machine-proven from neighbor geometry. [Automap reconstruction](https://github.com/Hyperbog/RLOFT/blob/dedebcbbe43b435e989e05c0a8b1ff9b8a611245/DatFiles/LEVELS.DAT/AUTOMAP.md)

## 15. CP437 is the export representation, not the internal map model

The exported bytes correspond to IBM/DOS text characters, but the internal automap does not store CP437 glyphs per cell.

The transformation is:

```text
cell word
    -> generated cache class
    -> connected resolver class
    -> export conversion table
    -> CP437-compatible output byte
```

This matters for native ports and editors: the text map should be treated as a presentation/export artifact, not as the canonical topology database.

## 16. Level automap style/control table

The fifth 64-word table in the fixed level header is:

```text
header +0x20A
DGROUP 0x25822
uint16 automap_style_control[64]
```

Automap drawing indexes it by the six-bit cell code, loads its two bytes into renderer state, and restores default values after the draw. [Automap reconstruction](https://github.com/Hyperbog/RLOFT/blob/dedebcbbe43b435e989e05c0a8b1ff9b8a611245/DatFiles/LEVELS.DAT/AUTOMAP.md)

All 2,048 entries across the 32 supplied level headers are `0xB5B1`.

That uniformity is a corpus fact, not a format law. A parser/editor must preserve arbitrary values.

## 17. Current-map display is rebuilt from live state

When the requested map equals current level global `0xC6C8`, map-browser routine `02AE8`:

1. calls `01558` to rebuild cache from the current live cell/dynamic state;
2. restores the current annotation buffer that was temporarily backed up;
3. retains current family-B placed-object state for overlays.

[Automap reconstruction](https://github.com/Hyperbog/RLOFT/blob/dedebcbbe43b435e989e05c0a8b1ff9b8a611245/DatFiles/LEVELS.DAT/AUTOMAP.md)

The displayed current map is therefore generated from **live world state**, not simply loaded from the last serialized cache.

## 18. Browsing another map uses a selective standalone snapshot reader

When selected map ID differs from current level `0xC6C8`, `02AE8` constructs:

```text
work\lev???.dat
```

using a normal hundreds/tens/ones three-digit substitution and opens that map's standalone level snapshot.

It selectively restores only the state needed by the map display:

- expanded family-B records for placed-object overlay;
- duplicated tail width/height;
- stored automap cache;
- stored annotation blob.

It does **not** activate that level, install its cell words as the gameplay world, or instantiate its NPCs. [Automap reconstruction](https://github.com/Hyperbog/RLOFT/blob/dedebcbbe43b435e989e05c0a8b1ff9b8a611245/DatFiles/LEVELS.DAT/AUTOMAP.md)

Thus the original game supports a **read-only historical automap snapshot** path independent of the normal level loader.

## 19. Current versus historical map architecture

The browser can be summarized as:

```text
requested map == active map

    current live LEVEL runtime
        |
        +-- rebuild cache with 01558
        +-- current family-B records
        +-- current annotations
        |
        v
    automap renderer


requested map != active map

    WORK\LEVnnn.DAT
        |
        +-- saved family-B overlay records
        +-- saved dimensions
        +-- saved automap cache
        +-- saved annotations
        |
        v
    automap renderer
```

This distinction is historically important. Viewing an older map does not require switching gameplay levels.

## 20. Map-title lookup

At map-load/browser setup, selected map ID is converted to text index:

```text
text_index = selected_map_id + 0x26D
```

and passed to the indexed text reader `1C368`, with decoded title stored in buffer `0x6058`. [Automap reconstruction](https://github.com/Hyperbog/RLOFT/blob/dedebcbbe43b435e989e05c0a8b1ff9b8a611245/DatFiles/LEVELS.DAT/AUTOMAP.md)

The map browser therefore obtains display names through the same indexed/XOR-decoded text-resource architecture used elsewhere in CODE.2 rather than storing level names in LEVELS.DAT.


## 21. Selected-map paging wraps and skips unavailable snapshots

Selected map ID is stored at `0x1274C`.

The paging controls adjust that ID through the level domain, wrap at the ends, and call map-loader `02AE8`. If the requested historical map has no readable `WORK\LEVnnn.DAT` snapshot, the control continues searching instead of instantiating the compact archive baseline as a substitute.

This preserves an important UI rule:

> the historical-map browser exposes maps with saved standalone map state, not every authored LEVELS.DAT record merely because it exists.

The active map is always available through the live path.

## 22. Current-map flag gates SAVE and PRINT

Runtime byte `0x5FCB` records whether the selected map is the active gameplay level.

The map SAVE and PRINT actions check this flag and return without performing their output operation when a historical/browsed map is selected.

Thus:

```text
current live map
    view
    save
    print

historical WORK\LEV snapshot
    view
    no current-map SAVE
    no current-map PRINT
```

This prevents browsing a stored historical snapshot from being confused with making that snapshot the current world.

## 23. Initial map viewport follows the party

On entering the automap, the selected map is initialized to current level/map `0xC6C8`.

The initial map viewport origin is derived from the high words of the player's live fixed-point world coordinates with an encoded offset of 24 cells.

The map is then regenerated through `01558` and drawn by the on-screen map renderer `0139C`.

The viewport is therefore initially centered/offset relative to the party's actual current cell rather than using a fixed level origin.

## 24. Automap scrolling

The automap scroll handler modifies the two viewport-origin components in two granularities:

```text
4 cells   fine scroll
40 cells  large/page scroll
```

and clamps the resulting origin against level bounds before redraw.

The exact input-bit assignments belong to the later input/UI chapter. The map-side behavior is already clear: navigation changes only the displayed source window, not the player's world position and not the stored exploration state.

## 25. On-screen cell scaling

Renderer `0139C` advances its two display coordinates by:

```text
8 units per source cell on one map axis
5 units per source cell on the other map axis
```

while walking the selected source rectangle.

This same geometry appears in annotation export lookup, which converts stored annotation coordinates using:

```text
map_x = raw_x / 8
map_y = raw_y / 5
```

with signed integer division/truncation toward zero. [Automap overlays](https://github.com/Hyperbog/RLOFT/blob/82abcbffbebee81936511b816b5ba6b6aa231a54/DatFiles/LEVELS.DAT/AUTOMAP_OVERLAYS.md)

The correspondence establishes that note coordinates are stored in the map renderer's scaled coordinate space, not directly as raw cell indices.

The archive does not need to assign modern Cartesian labels to the renderer's two internal screen axes beyond the proved `/8` and `/5` relationship.

## 26. On-screen annotation text is optional

Byte `0x5FD9` is toggled by a map UI action and tested by renderer `0139C`.

When nonzero, the renderer calls `01228`, which walks the annotation buffer at `0x5760` and draws annotation payload text using map-scaled placement and font-width logic.

Safe semantic identity:

```text
0x5FD9
    annotation-text display enabled
```

This is separate from the compact A/B/C... labels used by text export. The on-screen renderer can display note payload text directly.

## 27. Runtime annotation representation

The automap annotation list lives in a zero-filled `0x800`-byte runtime buffer at `0x5760`.

Each entry is:

```text
+0x00  int16 raw_x
+0x02  int16 raw_y
+0x04  int16 payload_length
+0x06  uint8 payload[payload_length]
```

A zero `payload_length` marks the in-memory terminator. [Automap overlays](https://github.com/Hyperbog/RLOFT/blob/82abcbffbebee81936511b816b5ba6b6aa231a54/DatFiles/LEVELS.DAT/AUTOMAP_OVERLAYS.md)

The level snapshot serializes:

```text
uint32 annotation_blob_length
uint8  annotation_blob[annotation_blob_length]
```

The zero-length terminator itself is not part of the serialized byte count; it exists because the runtime buffer is pre-zeroed after loading the preceding payload bytes.

## 28. Annotation size boundary

The level loader clears the complete `0x800` runtime annotation buffer and reads the serialized blob only when:

```text
serialized_length < 0x7FF
```

[Automap overlays](https://github.com/Hyperbog/RLOFT/blob/82abcbffbebee81936511b816b5ba6b6aa231a54/DatFiles/LEVELS.DAT/AUTOMAP_OVERLAYS.md)

This leaves room for the implicit terminating zero-length header within the zero-filled buffer.

A faithful editor should preserve this runtime bound rather than treating the serialized length as an arbitrary unbounded string field.

## 29. Supplied corpus contains no saved annotations

Across:

```text
all 32 LEVELS.DAT records
supplied LEV022.DAT
```

the serialized annotation length is zero. [Automap overlays](https://github.com/Hyperbog/RLOFT/blob/82abcbffbebee81936511b816b5ba6b6aa231a54/DatFiles/LEVELS.DAT/AUTOMAP_OVERLAYS.md)

Therefore the **format and runtime behavior** of annotations are executable-proven, but the supplied DAT corpus does not provide a naturally authored nonempty annotation fixture.

Regression tests for nonempty annotations must use constructed inputs that obey the proved layout rather than claiming such content came from the supplied save.

## 30. Text-export annotation labels

Export helper `023B8` walks the annotation list and matches map coordinates using:

```text
raw_x / 8
raw_y / 5
```

On a matching map cell it writes a sequential label into the annotation overlay buffer.

Labels begin as single letters:

```text
A
B
...
Z
```

then continue into a two-letter domain using the original routine's encoded increment order. [Automap overlays](https://github.com/Hyperbog/RLOFT/blob/82abcbffbebee81936511b816b5ba6b6aa231a54/DatFiles/LEVELS.DAT/AUTOMAP_OVERLAYS.md)

A port should reproduce the actual increment routine rather than replacing it with an assumed spreadsheet-column convention unless tests establish equivalence for the complete supported range.

## 31. Annotation legend uses the same label generator

Routine `02474` walks the same annotation records and emits the corresponding legend text:

```text
<label>:<payload>
```

using the same label progression as the map marker routine. [Automap overlays](https://github.com/Hyperbog/RLOFT/blob/82abcbffbebee81936511b816b5ba6b6aa231a54/DatFiles/LEVELS.DAT/AUTOMAP_OVERLAYS.md)

This guarantees that map marker and legend remain synchronized without storing the label itself in level data.

The label is derived from annotation-list order.

## 32. Placed-object overlay is family B

For each map cell whose cache state is not `0xFF`, exporter `026E8` repeatedly calls `00700`.

In the active level/map path, `00700` scans family B:

```text
base   0x22238
count  0x258A6
size   22 bytes per live record
```

and returns records whose stored cell coordinates match the requested cell. [Automap overlays](https://github.com/Hyperbog/RLOFT/blob/82abcbffbebee81936511b816b5ba6b6aa231a54/DatFiles/LEVELS.DAT/AUTOMAP_OVERLAYS.md)

This independently reinforces the family-B identity established in Component 05 as **placed object/item map records**.

## 33. Object overlay symbol selection

For each matching family-B record the exporter reads runtime type ID at `+0x0E` and writes:

```text
type 0x3C..0x41
    -> '*' (0x2A)

all other family-B types
    -> 0xFE
```

The supplied `OBJECTS.DAT` entries `0x3C..0x41` are:

```text
POTION OF EXTRA HEALING
POTION OF FIRE RESIST
POTION OF GIANT STRENGTH
POTION OF HEALING
POTION OF SPEED
OIL OF FIERY BURNING
```

[Automap overlays](https://github.com/Hyperbog/RLOFT/blob/82abcbffbebee81936511b816b5ba6b6aa231a54/DatFiles/LEVELS.DAT/AUTOMAP_OVERLAYS.md)

Thus `'*'` is a specially selected symbol for that six-entry consumable/liquid range.

Byte `0xFE` is the generic placed-object overlay value for the other family-B types. Community Ravenloft map research describes this display byte as the map's furniture/object glyph; the executable proves only its generic non-`0x3C..0x41` family-B use.

## 34. Multiple objects in one cell are order-sensitive

The exporter continues calling `00700` to obtain every matching family-B record for the cell.

Each matching object writes the same single overlay position, so later returned records replace the earlier symbol.

Therefore the final placed-object glyph is order-dependent when multiple placed records share one map cell. [Automap overlays](https://github.com/Hyperbog/RLOFT/blob/82abcbffbebee81936511b816b5ba6b6aa231a54/DatFiles/LEVELS.DAT/AUTOMAP_OVERLAYS.md)

A port should preserve family-B ordering if it aims to reproduce text output exactly.

## 35. Export has three conceptual layers

Exporter `026E8` builds:

```text
layer 1  base terrain/door/inset/floor glyphs

layer 2  placed family-B object symbols

layer 3  annotation marker labels
```

[Automap overlays](https://github.com/Hyperbog/RLOFT/blob/82abcbffbebee81936511b816b5ba6b6aa231a54/DatFiles/LEVELS.DAT/AUTOMAP_OVERLAYS.md)

In merged-file output the precedence is:

```text
annotation label
    > placed-object marker
    > base map glyph
```

Spaces in an overlay mean “do not replace the lower layer.”

## 36. Text export is column-oriented relative to native storage

The native cell index is row-major:

```text
cell_index = row * map_width + column
```

Exporter `026E8` allocates row buffers of length `map_height`, loops outer coordinate through `map_width`, and computes each source cell as:

```text
cell_index =
    inner_coordinate * map_width
  + outer_coordinate
```

[Automap overlays](https://github.com/Hyperbog/RLOFT/blob/82abcbffbebee81936511b816b5ba6b6aa231a54/DatFiles/LEVELS.DAT/AUTOMAP_OVERLAYS.md)

Thus the DOS text map is emitted in a column-oriented/transposed traversal relative to the native row-major array.

This is an export-layout fact and should be preserved when comparing generated `.MAP` files.

## 37. Merged file output

In map-file SAVE mode the exporter performs:

```text
result = base_glyph

if object_overlay != space:
    result = object_overlay

if annotation_overlay != space:
    result = annotation_overlay
```

and writes the complete merged buffer followed by:

```text
CR LF
```

[Automap overlays](https://github.com/Hyperbog/RLOFT/blob/82abcbffbebee81936511b816b5ba6b6aa231a54/DatFiles/LEVELS.DAT/AUTOMAP_OVERLAYS.md)

The saved automap is therefore a one-layer text image produced by destructively merging the three conceptual layers at export time.

## 38. Printer output deliberately overprints layers

In non-merged stream mode, the same exporter writes:

```text
base map line
CR

placed-object line
CR

annotation-label line
CR LF
```

[Automap overlays](https://github.com/Hyperbog/RLOFT/blob/82abcbffbebee81936511b816b5ba6b6aa231a54/DatFiles/LEVELS.DAT/AUTOMAP_OVERLAYS.md)

The first two carriage returns return the print head to the start of the same physical line **without advancing paper**.

The three layers therefore overprint one another on a conventional DOS text printer. Spaces in object/note lines leave the previously printed lower layer untouched.

This is not equivalent to printing three separate visible map rows.

## 39. PRINT uses Watcom `stdprn`

The direct PRINT caller at logical `03321` invokes exporter `026E8` in non-merged mode using fixed FILE-like runtime object `0xF764`.

The runtime contains five consecutive Watcom standard FILE objects:

```text
base = 0xF6F4
stride = 0x1C
```

and `0xF764` is the fifth object.

Open Watcom's DOS C Library documents the standard startup streams in this order:

```text
stdin
stdout
stderr
stdaux
stdprn
```

Therefore the fixed stream is the DOS standard printer stream, `stdprn`.

Official runtime documentation:  
<https://openwatcom.org/ftp/manuals/1.5/clib.pdf>

The game's automap PRINT path is consequently machine/runtime corroborated, not merely inferred from UI text or later community observation.

## 40. Map SAVE path template is embedded in CODE.2

CODE.2 contains the mutable path template:

```text
AUTOMAPS\AUTO???.MAP
```

at object-2/DGROUP `0x5FDA`, physical CODE.2 file offset `0x7BEFE` in the supplied executable.

Routine `02A34`:

1. derives three decimal digits from the current map/level value;
2. patches the three `?` bytes;
3. removes/recreates/opens the target file through runtime wrappers;
4. calls exporter `026E8` in merged mode;
5. closes the file.

[Automap reconstruction](https://github.com/Hyperbog/RLOFT/blob/dedebcbbe43b435e989e05c0a8b1ff9b8a611245/DatFiles/LEVELS.DAT/AUTOMAP.md) [Automap overlays](https://github.com/Hyperbog/RLOFT/blob/82abcbffbebee81936511b816b5ba6b6aa231a54/DatFiles/LEVELS.DAT/AUTOMAP_OVERLAYS.md)
